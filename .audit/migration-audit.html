Migration Engine Audit

A review of the migration subsystem: engine, schema builder, adapter, commands and dumper. Every defect below was reproduced against the real code, not inferred from reading it.

4Critical — silent data or schema damage
7High — wrong output or wrong ordering
9Medium — correctness & consistency
256DB tests green, none of these caught

Executive Summary

The architecture is genuinely strong, and unusually well-reasoned. The blueprint/adapter split holds: Blueprint describes, the adapter compiles, and Schema is the only static seam. The dbDelta() handling is the best-documented piece of WordPress-specific engineering I reviewed — the three parser rewrites, the foreign-key lift-out, and the reasoning about why an unnamed index cannot round-trip are all correct and all necessary. Batch allocation via a persisted high-water mark, the truthful half-applied-state contract, and the GET_LOCK() choice over an option row are the right calls, each defended by an argument rather than a preference.

The weakness is at the seams, not in the design. Four of the defects below are the same shape: a component is tested on its own, but the contract between two components is never executed. SchemaDumper builds an up() body and a down() body and then attaches both to up() — and the dumper's tests only run php -l, so syntactically valid, structurally inverted output passes. --pretend pins the schema adapter, but Migrator writes through raw $wpdb and never touches the adapter, so a dry run creates a real table. Blueprint has two nullable code paths, one of which drops authored defaults. And the migration sort key is a raw filename rather than the timestamp field the class exposes for exactly that purpose.

A fourth of the audit's weight sits in one blind spot: 256 database tests pass while all four critical defects are live. That is not an indictment of the suite's size — it is very thorough on the paths it covers — but of its two blind spots, both named in the findings: assertions that read a recorded-queries array rather than an executed result, and output tests that lint the generated code instead of running it.

Critical Vulnerabilities & Gaps

Critical

migrate:dump emits migrations that create a table, then immediately drop it

SchemaDumper.php:149 – 154, :564 – 599

dumpTable() returns one string — the Schema::create(...) call followed by the Schema::dropIfExists(...) from downBlock(). file() then interpolates that whole string into up() and leaves down() as a comment. So every dumped migration's up() is create then drop, and its down() does nothing at all. 

// generated output — up() contains the down() body
public function up(): void
{
    Schema::create('notes', function (Blueprint $table) {
        $table->id();
    });

    Schema::dropIfExists('notes');   // <-- belongs in down()
}

public function down(): void
{
    // Dropped newest-first by the migrator...   <-- empty
}

Failure scenario: an operator runs migrate:dump --path=… to capture a live schema, then runs the generated migration. It reports success, records itself as applied, and leaves no table. The down() is separately useless, so the migration also cannot be reversed. This inverts the command's entire stated purpose.

Why no test caught it: both dumper tests only assert the output parses. SchemaDumperTest.php:364 runs php -l and asserts exit status 0. Inverted output is perfectly valid PHP.

Critical

--pretend still creates the migration tracking table and burns a batch number

Migrator.php:240, :260, :946 – 980

Schema::pretend() pins and records through the schema adapter. But Migrator has no reference to the adapter at all — its only dependency is ?wpdb — and issues every tracking write with raw $db->query(). The adapter's recording mode therefore cannot see them. Confirmed by reflection: the migrator's constructor and properties contain no DatabaseAdapterInterface. 

$ wp wp_mini migrate --pretend        # operator expects: nothing written
CREATE TABLE `wp_plugin_migrations` ...  <-- REALLY executed
-- high-water option also bumped via update_option()

Failure scenario: a developer dry-runs a deploy against production to see what would happen. A table is created that did not exist. Separately, rememberBatch() at line 260 runs before the isPretending() guard at line 277, so update_option() is called for real and the next genuine migrate starts at a batch number one higher than it should — exactly the transcript-confusion the high-water mark exists to prevent.

The suite documents the correct behaviour and then fails to check it: the test at MigrationCommandsTest.php:343 says "no batch number is consumed by the dry run" and asserts only that the tracking table is empty, which no option write changes.

Critical

Two nullable paths silently discard the column's default

Blueprint.php:1112 – 1177

dropNotNull() strips NOT NULL, then strips any DEFAULT too unless the author set one explicitly. boolean() and id() carry a default from their type, and that default is removed. The intent — "a nullable boolean should report no answer, not false" — is right; the execution loses the type's default on every other type as well. 

$table->boolean('is_active')->nullable();
current : `is_active` tinyint(1)              // DEFAULT 0 lost

$table->string('slug')->default('draft')->nullable();
current : `slug` varchar(191) DEFAULT 'draft'  // no NULL / NOT NULL at all
expected: `slug` varchar(191) DEFAULT 'draft' NULL

Also reachable via makeNullable(), the by-name path used by nullableMorphs() — both morph columns are emitted as bare varchar(191) and bigint(20) unsigned with no nullability clause. A third defect there: line 1144 passes $column to dropNotNull(), whose second parameter is the column name; on the type-default branch the author default is indexed under the wrong key.

The nullableMorphs() test at WpDatabaseAdapterTest.php:1003 asserts exactly the buggy output — 'varchar(191)' — as correct, so the suite pins the defect as intended behaviour. boolean() has no test at all.

Critical

Mixed timestamp spellings run migrations out of chronological order

MigrationFile.php:71, :148; Migrator.php:883 – 886

MigrationFile accepts two timestamp forms and exposes timestamp() as "the batch-ordering key". But discover() sorts on identifier — the raw filename — and timestamp() is never called outside tests. The two forms do not interleave correctly, contrary to the docblock's claim. 

2026_11_05_999999_z     // Nov 5  (underscore form)
20261106000000_a        // Nov 6  (compact form) — LATER

strcmp order: 20261106000000_a  BEFORE  2026_11_05_999999_z
       // '_' (0x5F) > '1' (0x31), so the compact form always wins

Failure scenario: a project that has both forms — plausible, since both are accepted deliberately — gets migrations applied in the wrong order whenever the dates differ. Since the common use of a migration is "alter what the previous one created", this fails at the database, or worse, succeeds against the wrong shape.

A test exists at MigrationFileTest.php:125 named test_timestamps_sort_chronologically, but it performs the usort itself using timestamp() rather than calling the production path. It validates the field and never the ordering.

High

--pretend=off runs a real migration

MigrateCommand.php:79; MigrateFreshCommand.php:162

The falsy list is ['', '0', 'false', 'no'] — 'off' is missing, so it is read as truthy. migrate:fresh uses a different list that includes 'off'. Verbatim: --pretend=off → true → statements execute against the real database. The null case is worse than the inverse: the operator wrote "no" and got a live migration.

High

Only the least destructive command supports --pretend

Commands/Migrate*.php (survey)

migrate — which only creates — has --pretend. migrate:rollback, migrate:reset and migrate:refresh — which execute every migration's down(), the framework's most data-destructive path — have none. Nor do reset/refresh require --force, while migrate:fresh does. An operator about to reverse a production schema has no way to dry-run it, and no confirmation gate.

High

migrate:dump --path collides with WP-CLI's global --path

MigrateDumpCommand.php:160 – 169; README.md:832, :1277, :1446

WP-CLI consumes --path during bootstrap, as its own "wordpress root" flag, before handle() is called. The command's targetPath() reads $assocArgs['path'] and will never see it. The README documents this exact invocation in four places. Failure scenario: the operator follows the docs, gets "Please give a destination", and reasonably concludes the command is broken.

High

make:migration writes to a hardcoded directory

MakeMigrationCommand.php:312

base_path('database/migrations'), while Migrator takes its path by injection precisely so a project can relocate migrations — the provider docblock says so. Failure scenario: a project rebinds Migrator with a custom path; migrate reads the new path and make:migration writes to the old one. The generated file is never discovered, and nothing reports an error.

High

binary(n) dumps as blob

SchemaDumper.php:265; Blueprint.php:716

The type map discards the length and emits binary('%s'), and Blueprint::binary() emits blob NOT NULL. A binary(16) column — a UUID, a hash — round-trips to a different type, silently.

High

Dumper emits PHP syntax errors for backslash-containing defaults

SchemaDumper.php:378

str_replace("'", "\\'", $default) escapes quotes but not backslashes. A default of C:\ is emitted as ->default('C:\'), where the trailing backslash escapes the closing quote. php -l returns 255 on the dumped file — so the one check the dumper's tests do perform is the one that would catch this, and it is not run against data containing a backslash.

High

Dumper corrupts enum/set member values

SchemaDumper.php:331 – 341

trim($member, " '\"") strips spaces that are part of a member, so enum(' a ','b') dumps as ['a', 'b'] — a silently changed schema. MySQL's doubled apostrophe is not un-doubled either: enum('it''s') round-trips to ['it\'\'s']. Separately, set() has no case in builderCall() at all, so a table with a SET column cannot be dumped — it throws.

Medium

Command output is untestable, and one message is actively false

Command.php:48 – 65; MigrateStatusCommand.php:95

success()/error()/info()/warning() all guard on class_exists('WP_CLI'), which is false in the suite — deliberately, and documented. The consequence is that no command output is asserted anywhere, which is why the two output defects below shipped. Separately, migrate:status --pending counts $status after the filter has narrowed it, so with 5 migrations on disk and 2 applied it prints "3 migration(s) total, 3 pending". A deploy script reading that line as the README suggests gets a wrong total.

Medium

Failure arithmetic under --step reports the wrong story

MigrateCommand.php:125 – 147

With 3 pending and the second throwing, it prints "Recorded 1 of 3 migration(s); 2 stayed pending and will be retried." One of those two was attempted and failed, and "will be retried" describes a state that needs investigation as though it were routine. The follow-up warning at line 142 — "this batch recorded nothing, so it cannot be rolled back" — is guarded on $applied === [] (the whole run) rather than on the failed migration, so under --step it never fires even though the failing migration's batch number was burned.

Medium

rollback() reads the target batch outside the lock

Migrator.php:423 – 433

rollback() calls lastBatch() with no lock held, then delegates to rollbackBatch(), which acquires one. Between the read and the acquire, a concurrent migrate can allocate and populate a newer batch, so this rolls back a stale target. Narrow, but the class is otherwise careful about exactly this, and every other entry point wraps the whole operation.

Medium

Index names are derived by concatenation and can collide

Blueprint.php:2317 – 2322

implode('_', $columns) means index(['a_b','c']) and index(['a','b_c']) both produce a_b_c. The second silently replaces the first in MySQL's namespace, and a later dropIndex removes whichever exists. No length guard either, so a composite over long column names can exceed MySQL's 64-character limit and fail at the statement.

Medium

Two docblocks contradict the code they document

MigrationFile.php:143 – 147; MigrateFreshCommand.php:36

timestamp()'s docblock calls itself "the batch-ordering key" and asserts mixed spellings "sort the same either way" — both false, and both load-bearing to the defect above. migrate:fresh and migrate:reset both claim fresh never calls down(); Migrator::dropAllTables() at line 770 does. Three files now carry that second claim. This project has been bitten by docblock drift before, which is why it is listed rather than waved through as a comment nit.

Prioritized Action Plan

Tier 0

Stop the bleeding — data and schema integrity

before the next release
  1. Fix SchemaDumper::dumpTable() to return the up() and down() bodies separately, and have file() place each in its own method. Add a test that executes a dumped migration and asserts the table exists afterwards — the missing test is the reason this shipped.
  2. Route Migrator's tracking-table writes through DatabaseAdapterInterface, or add explicit Schema::isPretending() guards to ensureTrackingTable(), createTrackingTable() and both rememberBatch() calls. Whichever is chosen, add a test asserting that after --pretend the tracking table does not exist and the high-water option is unchanged.
  3. Correct dropNotNull() so only the intended type defaults are removed, and emit an explicit NULL. Fix the makeNullable() argument at line 1144. Add boolean()->nullable() coverage and correct the nullableMorphs() assertion that currently pins the bug.
  4. Sort migrations on timestamp() — the field that exists for it — in discover() and in rollbackBatch(). Add a mixed-spelling ordering test that calls the production path.
Tier 1

Close the correctness and usability gaps

next sprint
  1. Extract one flag parser and use it in all three commands. Add 'off', and test each flag with all six falsy spellings.
  2. Add --pretend to rollback, reset and refresh, and --force to reset and refresh. These run down(); they need the gate more than migrate did.
  3. Rename migrate:dump's destination flag to --output, update the four README examples, and note the collision in the error message.
  4. Give make:migration the migrator's resolved path instead of base_path() — inject it, or read it from the bound Migrator.
  5. Fix the dumper's binary/varbinary mapping, backslash escaping, and enum/set member handling; add a set case or fail with a clear message.
  6. Make rollback() read lastBatch() inside the lock. Fix the --pending total and the --step failure arithmetic.
Tier 2

Strengthen the seams that let these through

as capacity allows
  1. Introduce a way to assert command output — a small injectable output seam, or a WP_CLI stub in the test suite. Every output-path defect in this audit is currently unreachable by tests.
  2. Audit the adapter tests for the recorded-queries pattern. FakeWpdb::query() records into $queries before it parses, so assertStringContainsString(…, $db->queries) passes for any statement the fake cannot execute. Prefer assertions on the fake's parse result or on post-state over the raw recorded string.
  3. Add round-trip property tests: dump → replay → re-dump, asserting the two dumps are identical. That single test would have caught the inverted up(), the binary mapping and the escaping bug together.
  4. Add unit coverage for dropAllTables() (which calls down() and is untested), columnDefinition(), charsetCollation(), and the --pretend constraint-lift-out branch of createTable().
  5. Consider a shared helper for the falsy-flag list, a guard for the 64-character index-name limit, and a lint pass over generated migration files in CI.
On the four failing tests. The suite currently reports 1 error and 3 failures, all in the controller generator (GeneratedCodeTest, MakeControllerCommandTest) — consistent with the uncommitted controller work in the tree. The database subset is green at 256 tests / 556 assertions, independently confirmed. None of the defects above produce a failing test today.
Scope: framework/Database/**, framework/Console/Command.php, SchemaDumper, and the database test suite. Method: every finding reproduced by executing the real code path — reflection, a compile-then-inspect harness, or arithmetic traced against the engine's own bookkeeping. Nothing reported that could not be demonstrated.
