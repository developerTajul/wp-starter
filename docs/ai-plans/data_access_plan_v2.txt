# AI Task Orchestration Plan (v2.0): Data Access & Performance Layer

## 1. Architectural Corrections & Core Requirements Summary

### 1.1 The Repository Connection (Strict Layer Boundary)
- **Problem**: If the Fluent Query Builder is injected directly into the Service or Domain layers, framework agnosticism is broken.
- **Solution**: 
    - The Fluent Query Builder must be used **EXCLUSIVELY inside Repository implementations**.
    - It must never be injected into or used within the Service or Domain layers.
    - Repositories use the builder to fetch data but must map and return **Domain Entities**, never raw arrays.
    - **Recommendation**: Use dedicated `Mapper` classes to handle the conversion from raw array to Domain Entity to keep repositories lean.

### 1.2 Cache Decorator Pattern (Enforcing Decision #10)
- **Problem**: Calling `CacheInterface->remember()` inside the Service layer leaks infrastructure concerns into business logic.
- **Solution**: Caching must be implemented strictly via the **Decorator Pattern**:
    - `ProductRepositoryInterface` $\to$ `SqlProductRepository` (Actual DB & Query Builder logic).
    - `CachedProductRepository` (Decorator) $\to$ Implements `ProductRepositoryInterface`, wraps the inner repository, and uses `CacheInterface` to handle caching.
    - The Service layer remains completely oblivious to the caching mechanism.

### 1.3 Strict Query Builder Immutability
- **Problem**: Mutable query builders can suffer from side effects where `where` clauses bleed between different queries if the instance is shared.
- **Solution**: Strictly enforce immutability. Every chaining method (`where`, `select`, `join`, `orderBy`, etc.) **must return a cloned instance** (`return (clone $this)->withState(...)`).

### 1.4 Database Seeder & Cache Abstraction
- Implement `CacheInterface` wrapping WordPress Object Cache (`wp_cache_*`) and Transients API.
- Implement `make:seeder` and `db:seed` console commands for dummy data population during development.

## 2. Engineering Constraints & Guardrails

- **Strict Typing**: Every PHP file must start with `declare(strict_types=1);`.
- **SOLID & Clean Architecture**: Program to interfaces, use Constructor DI, and maintain strict layer separation (Domain $\leftrightarrow$ Infrastructure).
- **Immutability**: All Query Builder state transitions must be immutable via cloning.
- **Security**: Use `$wpdb->prepare()` for all dynamic values to prevent SQL injections.
- **Documentation**: Explicit English PHPDoc blocks required for all classes and methods.

### Critical Architectural Rules to Enforce:
1. **Strict Repository Boundary**: The Fluent Query Builder must be used EXCLUSIVELY inside Repository implementations (e.g., `SqlProductRepository`). Repositories must map raw query results into Domain Entities (preferably using a Mapper class) before returning them to the Service layer. Never inject the query builder into Service or Domain layers.
2. **Cache Decorator Pattern**: Implement caching exclusively via Decorator classes (e.g., `CachedProductRepository` wrapping `SqlProductRepository` both implementing `ProductRepositoryInterface`). Never call cache methods directly inside business/service logic.
3. **Strict Query Builder Immutability**: Every chaining method (`where`, `select`, `join`, `orderBy`, etc.) in the query builder must return a cloned instance (`return (clone $this)->...`) to prevent state mutation and side effects.
4. **Cache Abstraction & Seeders**: Implement `CacheInterface` (`WpCacheStore`) wrapping WP Transients and Object Cache, and implement seeder console commands (`make:seeder`, `db:seed`).

### Execution Sequence:
1. Inspect existing database adapters and repository contracts.

3. Implement `WpCacheStore` and the Repository Decorator pattern.

5. Run syntax checks (`php -l`) and verify that no infrastructure leaks exist in the Domain/Service layers.
